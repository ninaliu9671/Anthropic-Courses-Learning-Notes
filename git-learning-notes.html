Git 是什么？

本质：分布式版本控制系统

Git 是一个分布式版本控制系统（Distributed Version Control System）。用人话说，它就是一台"时光机"，可以记录文件的所有历史版本，让你随时回到过去。

核心理解： Git 不是"备份工具"，而是"历史记录系统"。它不是简单地复制文件，而是记录每一次修改的"快照"。

用历史编年的方式理解

想象你在写一部历史：

  • 没有 Git： 你手动创建 "历史_v1.docx"、"历史_v2.docx"、"历史_final.docx"、"历史_真的final.docx" — 混乱！
  • 有了 Git： 你只有一个 "历史.docx"，但 Git 在背后记录了每一个版本（公元100年、200年、300年...），可以随时查看或回退到任何时间点。

解决的问题：时光机 vs 手动备份

❌ 没有版本控制

  • 手动复制文件夹（project_v1, v2, v3...）
  • 不知道每个版本改了什么
  • 想回退很困难
  • 多人协作时容易冲突
  • 占用大量存储空间

✅ 有 Git

  • 只有一个文件夹，所有历史在 .git 里
  • 每次修改都有记录（commit message）
  • 一条命令回退到任何版本
  • 多人协作有成熟的合并机制
  • 压缩存储，节省空间

与 GitHub 的关系

我第一次听说的是 GitHub，但它和 Git 不是一回事。

Git 和 GitHub 的关系

  • Git： 本地的版本控制工具（2005年发明）
  • GitHub： 基于 Git 的云端协作平台（2008年上线）

类比理解：

  • Git = 你电脑上的文档编辑器（Word）
  • GitHub = 云端的文档协作平台（Google Docs）

关键区别：

  • Git 可以在完全离线的情况下工作
  • GitHub 需要网络，用于团队协作和云端备份
  • GitHub 应用了 Git 的核心机制，只是把存储位置从本地变成了云端
所以： 当你在本地文件夹看到 .git 时，说明这个项目正在用 Git 进行版本管理 — 即使你没连接 GitHub。

Git 的核心机制

.git 仓库 — 历史档案馆

当你在项目文件夹里看到 .git 文件夹时，这就是 Git 的"历史档案馆"。所有的版本历史都存储在这里。

重要理解： 你永远不在 .git 里工作！.git 是一个数据库，不是工作区。你看到和编辑的文件在工作区（项目文件夹），而 .git 只负责记录历史。

.git 文件夹的真实结构

你的项目/
├── src/              ← 工作区（你在这里写代码）
├── index.html        ← 工作区
├── README.md         ← 工作区
└── .git/             ← 仓库（Git 的历史档案馆）
    ├── objects/      ← 所有历史快照（压缩存储）
    ├── refs/heads/   ← 时间线标记（Branch）
    │   ├── main      ← 主时间线（一个文本文件）
    │   └── feature   ← 分支时间线（一个文本文件）
    ├── index         ← 暂存区（待发表区）
    └── config        ← 配置信息

objects/ — 历史快照存储

objects/ 文件夹存储了所有历史版本的文件内容（压缩格式）。每个 commit 就是一个完整的项目快照。

历史编年类比

objects/ = 历史卷宗柜

每个抽屉里存放一个时间点的完整历史记录（公元100年、200年、300年...）。这些记录是压缩存储的，节省空间。

refs/heads/ — 时间线标记

refs/heads/ 文件夹存储所有的 Branch（分支）。每个 Branch 只是一个几十字节的小文本文件，里面记录着它指向哪个 commit。

实际验证

打开 .git/refs/heads/main 文件，你会看到只有一行：

abc123def456789...（40个字符的 commit ID）

这就是"时间线标记"的真面目 — 它只是指向某个历史快照的指针。

index — 待发表区

index 文件就是"暂存区"，记录了哪些文件准备被提交到下一个历史快照。

三区域模型

Git 的工作流程涉及三个"区域"，理解这三个区域是掌握 Git 的关键。

工作区 (Working Directory)
   ↓ git add
暂存区 (Staging Area)
   ↓ git commit
仓库 (Repository)

工作区 — 历史学家的写作台

  • 位置： 你能看到和编辑的文件（项目文件夹）
  • 作用： 实际写代码、修改文件的地方
  • 特点： 可以随意修改，Git 会检测到变化但不会自动记录

历史编年类比

工作区 = 历史学家的写作台

你在这里撰写新的历史记录、修改已有的内容。这些修改还没有正式"发表"，只是草稿。

暂存区 — 待发表区

  • 位置： .git/index 文件（你看不到实际内容）
  • 作用： 标记准备提交的文件
  • 特点： 可以检查、调整，确认无误后再正式提交

历史编年类比

暂存区 = 待发表区

你把撰写好的历史内容放入"待发表区"，可以校对、修订，确认无误后再正式载入史册。

仓库 — 历史卷宗

  • 位置： .git/objects/ 文件夹（压缩存储）
  • 作用： "时光机数据库"，永久记录所有历史版本
  • 特点： 一旦提交，就永久保存，可以随时回退

历史编年类比

仓库 = 历史卷宗

正式发表的历史记录都保存在这里，每个时间点都是完整的快照，可以随时查阅。

文件状态流转

文件在这三个区域之间流转，会经历不同的状态。

Untracked (未追踪)
    ↓ git add
Staged (已暂存)
    ↓ git commit
Committed (已提交)
    ↓ 继续修改
Modified (已修改/未暂存)
    ↓ git add
Staged (已暂存)
Untracked（未追踪）
新创建的文件，Git 还不认识它。就像新写的历史草稿，还没提交给编辑部。
Staged（已暂存）
用 git add 标记的文件，在暂存区等待提交。就像放入"待发表区"的历史稿件。
Committed（已提交）
用 git commit 正式保存的文件，在仓库里永久记录。就像正式载入史册的历史事件。
Modified（已修改/未暂存）
已有文件被修改了，但还没 git add。就像修改了已发表的历史，但还没提交修订版。
关键理解：
  • Untracked： Git 不知道这个文件的存在
  • Modified： Git 知道这个文件，但检测到它被修改了

时间线的秘密：Branch

Branch = 时间线标记（不是副本）

Branch（分支）是 Git 中最容易被误解的概念。我原来以为"创建分支 = 复制整个项目"，但这是错误的。

我的误解： Branch 是复制整个项目，所以创建10个 Branch 会占用10倍空间。
实际情况： Branch 只是一个"时间线标记"，创建10个 Branch 只增加几百字节。

历史编年类比

Branch = 历史时间线的标记

想象历史有多条时间线（正史、平行宇宙）：

  • main 分支 = "正史"标记 — 指向当前的历史年代（比如公元2026年）
  • feature 分支 = "平行宇宙"标记 — 指向另一条时间线的某个时间点

这些标记只是"书签"，不是复制整部历史。

空间占用验证

假设你的项目有 1GB 的文件：

  • .git/objects/（所有历史快照）： 500 MB
  • .git/refs/heads/main（Branch 文件）： 40 字节
  • 创建 10 个 Branch： 只增加 400 字节（10 × 40）

如果是复制： 应该增加 10 GB！

Commit 链 — 历史事件的母子关系

每个 Commit（提交）不是孤立的，它们通过"母子关系"连接成一条链。

main 分支 ──→ Commit 4（最新）
              ↓ 母指针
            Commit 3
              ↓ 母指针
            Commit 2
              ↓  母指针
            Commit 1（初始）

数据结构解析

  • Branch： 只知道"我指向哪个最新的 Commit"
  • Commit： 知道"我的母节点是谁"
  • 查找历史： 从 Branch 指向的 Commit 开始，沿着母指针往回走
为什么这么设计？
  • Branch 不需要记住所有 Commit（节省空间）
  • 只要记住最新一个，顺着"母指针"就能找到全部历史
  • 创建新 Branch 只需创建一个新指针（瞬间完成）

Branch 文件的真实内容

让我们看看 Branch 文件到底是什么：

打开 .git/refs/heads/main 文件

abc123def456789ghi012jkl345mno678pqr901st

这就是全部内容 — 40个字符的 commit ID。

这40个字符是什么？它是一个 SHA-1 哈希值，指向 .git/objects/ 里的某个历史快照。

历史编年类比

Branch 文件 = 历史年代标记

就像你在历史书上贴了一个书签，上面写着"公元2026年"。这个书签本身只占一张纸的空间，但它能帮你快速找到那个年代的所有历史记录。

设计哲学 — 为什么这么设计？

Q：为什么不让 Commit 记住自己属于哪个 Branch？

❌ 如果 Commit 记住 Branch

  • 一个 Commit 可能属于多个 Branch（复杂）
  • 创建 Branch 需要修改历史所有 Commit（低效）
  • 删除 Branch 需要遍历所有 Commit 更新记录（危险）

✅ Branch 指向 Commit 的优势

  • 创建 Branch：瞬间完成（只需创建一个指针）
  • 删除 Branch：只需移除指针（Commit 还在）
  • 切换 Branch：快速（只需移动指针）
  • Commit 数据：永远不变（稳定）
每次 Commit，Branch 文件会自动更新：
  1. 你运行 git commit
  2. Git 创建新的 Commit 对象（保存在 .git/objects/）
  3. Git 更新 .git/refs/heads/main 文件，把里面的 commit ID 改成新的

工作流程

基本流程：编辑 → add → commit

Git 的基本工作流程很简单，但每一步都有其意义。

1. 工作区编辑文件
   ↓
2. git add（选择要提交的文件）
   ↓
3. 暂存区（检查、调整）
   ↓
4. git commit（拍照保存）
   ↓
5. 仓库（永久记录）

实际例子

场景：你同时修改了5个文件，但想分两次提交

# 第一次提交（登录功能）
git add login.js auth.js
git commit -m "feat: add login feature"

# 第二次提交（首页优化）
git add home.js style.css utils.js
git commit -m "refactor: optimize homepage"

为什么分两次？

  • 原子性： 每个 commit 只做一件事
  • 可读性： 历史记录清晰
  • 可回退： 出问题只回退相关部分

为什么需要暂存区？

Q：为什么不能直接从工作区 commit，而需要先 git add？

核心答案： 暂存区提供了一个"检查和调整"的缓冲区，让你能更精细地控制每次提交的内容。

原因1：可检查性

没有暂存区

改了10个文件 → 直接 commit → 发现有个文件不该提交 → 太晚了！

有暂存区

改了10个文件 → git add 5个 → git diff --cached（检查暂存区）→ 发现问题 → git reset 某个文件 → 重新 add → 再 commit

原因2：部分提交

场景：一个文件改了100行，只想提交前50行

login.js:
- 前50行：添加登录功能 ✅
- 后50行：调试代码 ❌（不想提交）

# 解决方案
git add -p login.js  # 选择只添加前50行
git commit

如果没有暂存区： 只能提交整个文件，或者手动删除后50行再提交（麻烦！）

原因3：原子性保证

暂存区 = 待发表区

历史编年类比：

  • 工作区 = 写作台 — 所有草稿（修改的文件）
  • 暂存区 = 待发表区 — 你选中的稿件
  • 仓库 = 历史卷宗 — 正式发表后的记录

你可以：

  • 从写作台拿稿件到待发表区（git add）
  • 从待发表区拿出不要的（git reset）
  • 确认后正式发表（git commit）

版本回退

Git 的"时光机"功能体现在版本回退上。有三种回退方式：

你的提交历史：
C3 (最新) ← HEAD
 ↓
C2
 ↓
C1
 ↓
C0 (最早)

方式1：软回退（保留代码）

git reset --soft C2

结果：

  • 代码还在工作区（C3的修改都还在）
  • 只是"取消"了C3这次提交
  • 可以重新修改后再 commit

历史编年类比

就像历史学家说："我要撤回刚才发表的那段历史（C3），重新修改后再发表。"内容还在写作台上，只是没有正式载入史册。

方式2：硬回退（彻底删除）

git reset --hard C2

结果：

  • 代码回到C2的样子
  • C3的所有修改都消失了（危险！）
警告： 硬回退会永久丢失C3的修改！使用前务必确认。

方式3：查看历史版本（不修改）

git checkout C1

结果：

  • 你能看到C1时的代码
  • 但没有修改历史
  • 像"时光旅行"去参观

历史编年类比

就像历史学家翻开史册，查阅"公元100年"的历史记录，但不修改它。看完后可以回到当前年代（git checkout main）。

Merge — 合并平行时间线

当你有多个 Branch（时间线）时，最终需要把它们合并到一起。

main:  C1 ← C2 ← C3 ← C4
feature: C1 ← C2 ← C3 ← C5 ← C6

git merge feature（在 main 分支执行）
    ↓
main:  C1 ← C2 ← C3 ← C4 ←─┐
                           ├─ C7（merge commit）
feature: C1 ← C2 ← C3 ← C5 ← C6

历史编年类比

Merge = 合并平行时间线的历史

想象历史有两条时间线：

  • 正史（main）： C1 → C2 → C3 → C4
  • 平行宇宙（feature）： C1 → C2 → C3 → C5 → C6

Merge 就是把"平行宇宙"中发生的事件（C5、C6）合并到"正史"中，创建一个新的历史节点（C7）记录这次合并。

为什么需要 Merge？

虽然所有 Commit 都在同一个 .git 里，但它们属于不同的"时间线"（Branch）。Merge 的作用是把两条时间线的修改合并到一起。

Worktree — 同时研究多条时间线

什么是 Worktree

Worktree 是我最初感到困惑的概念之一。在用 Claude Code 时，突然出现了 worktree-login/ 这样的文件夹，我不知道它是什么。

核心理解： Worktree = Branch 的物理"研究室"。它让你可以同时在不同的文件夹里查看和编辑不同的 Branch，而不需要来回切换。

历史编年类比

Worktree = 不同的历史研究室

想象你是历史学家，需要同时研究两条时间线：

  • 主研究室（主文件夹）： 研究"正史"（main 分支）
  • 分研究室（worktree 文件夹）： 研究"平行宇宙"（feature 分支）

两个研究室共享同一个历史档案馆（.git），但可以同时打开不同的历史卷轴（Branch）。

Worktree vs 传统 Branch

传统 Branch（切换方式）

项目文件夹/
├── src/
└── .git/

git checkout feature
→ 文件夹内容瞬间变化
→ 同一个研究室，换不同的历史卷轴

Worktree（并行方式）

主项目/
├── src/
└── .git/

worktree-feature/
├── src/
└── (指向同一个 .git)

→ 两个独立文件夹
→ 两个研究室，同时研究不同的历史

何时使用 Worktree

场景1：不需要 Worktree

你在做一个功能，做完再做下一个

建议： 不开 Worktree，直接在主文件夹工作

场景2：需要 Worktree

功能A 开发中，卡住了；你想先做功能B，但不想影响功能A的进度

建议： 开 Worktree！

  • 主文件夹：功能A 的半成品（继续保留）
  • Worktree-1：功能B 的独立空间（互不干扰）
注意冲突： 如果两个 Worktree 都改了同一个文件，合并时会出现冲突，需要手动解决（或让 AI 帮忙）。

Worktree 操作流程

创建 Worktree

git worktree add worktree-login login-branch

发生了什么？

  1. Git 创建一个新文件夹（worktree-login/）
  2. 从 .git 提取（解压） login 分支的所有文件
  3. 两个文件夹指向同一个 .git 数据库
重要： Worktree 检出（checkout）的是整个项目，不是部分文件！即使你只改一个文件，整个项目结构都会被检出。

在 Worktree 里工作

cd worktree-login/
# 修改文件
git add login.js
git commit -m "feat: add login"

这次 commit 保存在哪里？

保存在 .git 的 login 分支里，不是 main 分支。

合并回主分支

cd ~/project/  # 回到主文件夹
git merge login  # 合并 login 分支到 main

删除 Worktree

# 方式1：直接删除文件夹
rm -rf worktree-login/

# 方式2：用 Git 命令删除
git worktree remove worktree-login
删除 Worktree 后，代码还在吗？
  • 已 git commit： 代码保存在 .git 的 login 分支里，删除 Worktree 不影响
  • 已 git add 但未 commit： 暂存区的内容还在 .git 里
  • 只修改了文件，没 git add： 删除 Worktree = 丢失修改

运行项目时用的是哪个版本？

场景对比

# 场景1：在主文件夹运行
cd ~/project/
npm start
→ 运行主文件夹（main 分支）的代码

# 场景2：在 Worktree 文件夹运行
cd ~/project/worktree-login/
npm start
→ 运行 worktree-login 文件夹的代码

# 可以同时运行！
→ 主文件夹：localhost:3000
→ Worktree：  localhost:3001
核心理解： 运行的永远是工作区的文件！Git 的 commit/暂存区与运行无关。

Git 与 GitHub

GitHub 的定位

现在回到最初的问题：Git 和 GitHub 到底是什么关系？

核心关系

  • Git： 本地的版本控制工具（本地的历史档案馆）
  • GitHub： 应用了 Git 机制的云端协作平台（云端的历史档案馆）

GitHub 的核心功能就是把 .git 仓库从你的电脑复制一份到云端，让团队成员可以共享和协作。

本地 Git vs 云端 GitHub

本地 Git（.git 文件夹）
    ↕️  git push / git pull
GitHub（云端仓库）

本地 Git

  • 在你的电脑上
  • 不需要网络
  • 只有你能访问
  • 完全独立工作

云端 GitHub

  • 在 GitHub 服务器上
  • 需要网络
  • 团队成员可以访问
  • 用于协作和备份

为什么本地也能用 git 命令

这是我最初的困惑：为什么我没连 GitHub，本地也能用 git 命令？

答案： 因为 Git 是本地工具，所有操作（add、commit、branch）都在本地的 .git 文件夹里完成，不需要 GitHub。

GitHub 只是一个可选的"云备份+协作"平台。你可以：

  • 只用 Git，不用 GitHub
  • 用 Git + GitHub（推送到云端）
  • 用 Git + 其他平台（GitLab、Bitbucket）

实践问题集

AI Agent 陷入死循环怎么办

这是我实际遇到的问题：Claude Code 运行了十几个小时，没解决问题，产生了很多"未追踪文件"和"未暂存文件"。

发生了什么？

  • Claude Code 创建了很多临时文件、测试文件
  • 修改了现有文件
  • 但没有完成 git commit（因为任务没完成）

处理方案1：全部保留

告诉 AI：
"分析这些未追踪和未暂存的文件，
保留有用的，删除临时文件，然后提交"

AI 会：
1. 读取所有文件
2. 删除 .log、.tmp 等临时文件
3. git add 保留的文件
4. git commit

处理方案2：全部丢弃

git reset --hard  # 丢弃所有未暂存的修改
git clean -fd     # 删除所有未追踪的文件

处理方案3：部分保留

告诉 AI：
"只保留 login.js 和 auth.js，其他都丢弃"

AI 会：
git add login.js auth.js
git commit -m "feat: partial login implementation"
git clean -fd  # 删除其他未追踪文件

如何判断该保留什么？

策略1：问 AI 当前进度

"总结一下你现在做到哪一步了，
哪些功能已经完成，哪些还没做"

策略2：让 AI 分类文件

"把现在所有改动的文件分成三类：
1. 完成的功能（可以保留）
2. 半成品（需要判断）
3. 临时调试文件（可以删除）"

策略3：查看 Git 状态

"运行 git status，然后解释每个文件的状态"

💡 Tip：用 Subagent 评估中间态文件

场景：AI Agent 陷入死循环，产生大量未追踪/未暂存文件

最佳做法：在当前对话窗口让主 Agent 调用 Subagent Code Reviewer

你："停下来！调用 Subagent Code Reviewer，
评估现在的代码状态，告诉我哪些该保留"

为什么用 Subagent？

  • 有任务上下文：知道你要实现什么功能、当前进度
  • 没有执行历史：不受"这是我尝试过的"这种认知惯性影响
  • 客观评估：fresh pair of eyes，只看代码质量和对目标的贡献

⚠️ 注意：主 Agent 的推理链会被自己的历史锁定（认知路径依赖）。Subagent 没有这个问题，因为它只接收任务目标和当前状态，不接收主 Agent 的思考过程。

多 AI Agent 协作导致混乱

我同时用了 Claude Code、Codex、Cursor，结果代码库变得一团糟。

为什么会混乱？

  • 每个 Agent 都在工作区修改文件
  • 没有及时 commit，导致修改堆积
  • 不同 Agent 的修改可能冲突

最佳实践：规则1

一个 Agent 完成任务后再用另一个 
# ✅ 正确流程
Claude Code 完成登录功能
 ↓
git add + git commit
 ↓
切换到 Cursor 优化首页
 ↓
git add + git commit

最佳实践：规则2

使用不同的 Branch 
# Claude Code 用 feature-login 分支
git checkout -b feature-login
Claude Code 工作...
git commit

# Cursor 用 feature-homepage 分支
git checkout -b feature-homepage
Cursor 工作...
git commit

# 最后合并
git checkout main
git merge feature-login
git merge feature-homepage

最佳实践：规则3

定期 commit

不要等所有功能完成才 commit，每完成一个小功能就 commit 一次。

在 Claude Code 里如何 Commit

方式1：让 Claude Code 自动处理

你: "测试通过了，帮我 commit 并推送到 GitHub"

Claude Code 会：
1. 运行 git add .（添加所有修改）
2. 生成符合规范的 commit message
3. git commit -m "feat: add user authentication"
4. git push origin main

方式2：手动指定要提交什么

你: "只提交 src/auth.js 和 src/login.js，
    其他文件先不要动"

Claude Code 会：
git add src/auth.js src/login.js
git commit -m "feat: implement OAuth login flow"
