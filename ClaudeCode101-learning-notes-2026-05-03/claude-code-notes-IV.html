Claude Code 学习笔记 IV

把 I/II/III 的所有知识整合成一张地图，然后用一个真实项目把它们全部用上
模块一

全景地图 — 所有概念之间的关系

学完 I/II/III 之后，你接触了十几个概念。单独看每一个都能理解，但放在一起就容易乱。这一模块不重复解释概念，只给一个新视角：它们之间的关系是什么，以及各自在整个系统里扮演什么角色。

1.1　Claude Code 的三层结构

把所有工具摊开来看，会发现它们天然分成三层，每层解决一类不同的问题：

┌─────────────────────────────────────────────────────────────┐ │ 扩展层 │ Skills · MCP · Subagent · Hooks │ │ 扩展能力边界——让 Claude 能做更多、更准确、更自动化 ├─────────────────────────────────────────────────────────────┤ │ 记忆层 │ Context Window · CLAUDE.md · Auto Memory · Persistent Memory │ │ 解决遗忘问题——让 Claude 在需要时知道该知道的事 ├─────────────────────────────────────────────────────────────┤ │ 执行层 │ Claude 本体（LLM，无状态） │ │ 理解任务、制定计划、决定下一步——但本身什么都不记得 └─────────────────────────────────────────────────────────────┘

三层之间的关系是：记忆层解决了执行层的先天缺陷（无状态），扩展层在记忆层之上进一步放大 Claude 的能力上限。没有记忆层，Claude 每次都从零开始；没有扩展层，Claude 只能做到本地代码库的边界为止。

为什么先有"记忆层"才有"扩展层"：Skills、MCP、Subagent 这些扩展工具，都依赖 Claude 有稳定的"背景知识"才能正确使用。如果 Claude 连项目规范都记不住，扩展再多工具也是徒劳。所以正确的搭建顺序是：先把记忆层（CLAUDE.md + Memory）建好，再往上叠扩展层。

一个工具可以同时扮演多个角色。MCP 既是"输入信息"（工具定义加载进 context），也是"执行动作"（实际发起 API 调用）。Subagent 既是"执行动作"（完成一个独立任务），也是"控制边界"（把探索过程隔离在独立 context 里）。分角色理解，是为了知道它在这一刻在做什么，而不是给工具贴固定标签。
记忆层里的工具那么多，它们在"给 Claude 喂信息"这件事上有什么区别？
核心区别在于谁来写、什么时候喂、喂给谁：

CLAUDE.md — 你写，每次启动就喂，给所有对话用
Auto Memory — Claude 自动写，每次启动就喂，给主 Agent 用
Persistent Memory — Subagent 按指令写，Subagent 启动时喂，给特定 Subagent 用
Skills — 你写，按需喂（只在 Claude 判断需要时），给当次任务用
Context Window — 自动积累，整个 session 都在，给当次 session 用

五条线都是"把文字喂进模型的视野"，但时机、来源、目标各不相同。这就是为什么需要五种机制，而不是一种。
模块二

综合辨析 — 最容易混淆的六对概念

概念单独看都能理解，放在一起就容易混。这里不重复解释每个概念，只聚焦一件事：它们在哪里看起来相似，核心区别究竟在哪，什么情况下选哪个。

对比 1　CLAUDE.md vs Memory

CLAUDE.md vs Memory（Auto Memory）
同
都是跨 session 持久化，都在每次新对话启动时自动注入 system prompt，都在解决"Claude 对你一无所知"的问题
异
你手动写
你知道要写什么，主动维护
Claude 自动写
Claude 边工作边判断"这件事值得记"，主动写入
异
静态规则
技术栈、规范、命令——不会自动更新
动态经验
用户偏好、踩过的坑、项目隐性约定——随使用深入而积累
异
除非你改，否则永远有效
可能过时，需要 Dream Agent 定期整理，与现实对齐
怎么选：你明确知道"Claude 必须遵守这条规则"→ CLAUDE.md；你想让 Claude 自己在工作中积累"这个项目的潜规则"→ 让 Memory 自动处理。两者不是竞争，是互补——一个是你写的入职手册，一个是 Claude 自己记的工作日志。

对比 2　Skills vs CLAUDE.md

Skills vs CLAUDE.md
同
都是你写给 Claude 的知识，都存在项目的文件里，都影响 Claude 执行任务的方式
异
按需加载，用完即弃
启动时只加载目录，用时才加载完整内容，不一直占 context
永远在 context
启动时全部注入，不管这次用不用得上，每次都占空间
异
执行方法（怎么做某件具体的事）
小红书文案怎么写、代码审查怎么做

用 pnpm、不改测试快照、先探索再写代码
异
可跨项目复用
一个"写文档"的 Skill，任何项目都能用
项目特定
通常和代码库一起提交，是这个项目的专属配置
怎么选：每次对话都要遵守的规范 → CLAUDE.md；只有特定任务类型才需要的详细方法，且不想每次都占 context → Skills。一个粗略的判断标准：如果你发现某条 CLAUDE.md 规则只在某类任务时才有用，把它拆出来做成 Skill。

Skills vs MCP

怎么选：你需要教 Claude 一套可复用的方法论 → Skills；Claude 需要读取不在本地的数据或调用外部 API → MCP。两者经常一起用：MCP 负责拿到外部数据，Skills 负责告诉 Claude 拿到数据之后该怎么处理。

对比 4　Subagent vs 新开对话

Subagent vs 手动新开对话
同
都是一个全新的 Claude 实例，都有干净的、独立的 context window，都不带当前对话的历史负担
异
主 Agent 自动传入背景
任务描述、项目信息由主 Agent 打包好传进去，一启动就知道背景
你手动解释背景

异
结果自动返回
完成后 summary 直接回到主 Agent，工作流不中断
结果需要你中转
手动复制结果，粘贴回主对话，你成了那个"桥梁"
异
临时任务，做完即弃
Context 用完丢弃，除非配置了 Persistent Memory
新的持续工作
读取 Auto Memory，进入正常会话生命周期
怎么选：有一个明确的子任务，需要独立执行后把结果汇报回来（Code Review、并行探索）→ Subagent；要开始一项和当前任务无关的全新工作 → 新开对话。判断标准：工作流是否需要连续？需要就用 Subagent，不需要就新开。

对比 5　Hooks vs CLAUDE.md 提示

Hooks vs CLAUDE.md 里的提示
同
都能让某些事情"在 Claude 工作时发生"，都可以用来设置"做完 X 之后做 Y"这类行为规范
异
100% 确定执行
事件触发，系统层面强制执行，不经过 Claude 判断
概率性执行
Claude 读到规则，大部分时候照做，但会忘、会跳过、会看情况
异
机械动作，不需要理解内容
运行 prettier、记日志、发通知——只看动作类型和文件路径
需要 Claude 智能判断
"适当时候给出风格建议"、"如有必要则重构"——需要理解上下文
异
shell 命令，写在 settings.json
执行者是操作系统，不是 Claude
自然语言指令，写在 CLAUDE.md

怎么选：这件事必须每次都发生，不允许例外，且是纯机械动作 → Hooks；这件事需要 Claude 理解情况后灵活判断是否要做、怎么做 → CLAUDE.md。发现自己在 CLAUDE.md 里写"每次 X 之后必须 Y"，就该问自己：为什么不用 Hook？

对比 6　/compact vs Memory

/compact（上下文压缩） vs Memory（持久化记忆）
同
都和"让 Claude 记住更多东西"有关，都会在压缩/整理过程中保留"重要信息"，都是解决遗忘问题的手段
异
Session 内压缩
释放 context 空间，在当前对话内继续工作
跨 Session 持久化
关掉窗口重新打开，信息仍然存在
异
自动或手动触发
context 满时自动压缩，或用 /compact 主动执行
主动设计
Claude 自己判断写（Auto Memory），或 Subagent 按指令写
异
压缩的是"对话历史"
把几千 token 的对话摘要成几百 token 的摘要
提炼的是"值得记住的经验"
以结构化文件形式保存，供未来的 session 使用
怎么选：Context 快满了，当前任务还没完成，不想丢失工作状态 → /compact；想让这次对话中发现的经验或偏好，在未来的对话里也能用到 → Memory（让 Claude 自动写，或者你明确提示它记下来）。一个常见误解：以为 /compact 能解决跨 session 的遗忘——不能，它只管当前这个 session 内的空间问题。
模块三

决策框架 — 遇到问题选哪个工具

有了全景地图和辨析清单，接下来的问题是：真实场景里怎么快速做决定？这里不从工具出发，而是从你的需求出发——描述你想解决什么问题，直接指向答案。

记忆 · 知识管理
想让 Claude 记住项目规则，每次启动都知道 → CLAUDE.md
想让 Claude 记住它踩过的坑和我的偏好，不用我操心 → Auto Memory（它自己会记）
想让某个 Subagent 跨 session 记住项目历史，团队共享 → Persistent Memory（project scope）
想给 Claude 一套可复用的执行方法（不想每次都塞进 context） → Skills
能力扩展
想让 Claude 读取 Linear / 数据库 / 外部服务的数据 → MCP
想让 Claude 查询最新的库文档、不在本地的任何数据 → MCP（Context7 等文档服务）
任务隔离 · 执行控制
想让某个子任务在独立空间执行，不污染主对话的 context → Subagent
想让代码写完后自动格式化，100% 不漏，不依赖 Claude 记得 → Hooks（PostToolUse）
想阻止 Claude 执行某类危险命令，从源头拦截 → Hooks（PreToolUse，exit code 1）
想在 Claude 完成任务后收到通知，去做下一件事 → Hooks（Stop）
Context 管理
Context 快满了，当前任务还没完成，不想丢工作状态 → /compact
当前任务已完成，要开始全新的不相关任务 → /clear（先确认重要规则已在 CLAUDE.md 里）
MCP 工具占了太多 context，但用不到那些服务 → 用 /mcp 关闭不用的 MCP 服务器
工具可以叠加使用，不是非此即彼。一个真实场景往往需要多个工具配合：
CLAUDE.md（项目规范）
+ Skills（小红书文案写法）
+ Subagent（Code Review 独立视角）
+ Hooks（每次写完文件自动格式化）
+ /compact（长任务中途释放空间）
= 一套完整的工作流 单独讨论"用哪个"只是入门，真正的掌握是知道在这个具体 workflow 里，每个工具做它最擅长的那部分。
很多场景好像都能用 CLAUDE.md 解决，什么情况下值得多学其他工具？
CLAUDE.md 确实是"万能胶"——把什么都往里塞，大多数时候 Claude 会照做。但这有两个代价：

1. Context 代价：塞进去的所有内容每次都占 context 空间，10条规则就是10条规则的常驻成本，不管这次用不用得上。Skills 的按需加载就是解决这个问题的。

2. 可靠性代价："请每次编辑文件后格式化"写进 CLAUDE.md，Claude 大部分时候会做，但不是 100%。如果你发现某件事"反正必须发生，不能漏"，那就该改用 Hooks。

CLAUDE.md 是好的起点，其他工具是当 CLAUDE.md 开始显露出不够用的时机时的升级路径。
模块四

大实践 — 搭建学习笔记 Workflow

概念到位了，现在来真正用一遍。这一模块把前三篇的所有工具串进一个真实项目——你现在正在做的学习笔记 Workflow。它不是假设的例子，而是一套你可以立刻搭起来的配置。

项目背景

Workflow 目标 输入：每节课的学习资料（Markdown + 图片）+ HTML 笔记 ↓ 输出一：章节总结 HTML（深度学习笔记，按知识脉络整理） 输出二：小红书内容包（8–10 张配图 prompt + 配套文案） // 为什么这个 workflow 是好的练习场？ // 它同时涉及：规范要求（CLAUDE.md）+ 可复用方法（Skills） // + 必做操作（Hooks）+ 子任务隔离（Subagent） // 所有工具都有用武之地，不是为了用而用

我们把整个搭建过程分成五个阶段：Explore → Plan → Code → 使用中的记忆管理 → Troubleshooting。这个顺序本身就是笔记 I 教的工作流——用来搭建 workflow 的工具，和 workflow 里用到的工具，是同一套。

阶段一

Explore — 探索需求，做工具选型

在 Plan Mode 下，用自然语言把你的 workflow 目标告诉 Claude，让它帮你分析需要哪些工具。不要直接跳到配置——先把需求说清楚，让 Claude 替你想清楚。

你说的话（示例）：

// 给 Claude 的 prompt 我在做一个学习笔记 workflow： - 输入：每节课的 Markdown 资料 + HTML 学习笔记 - 输出：章节总结 HTML + 小红书内容包（文案 + 配图 prompt） 帮我分析： 1. 这个 workflow 需要哪些 Claude Code 工具？ 2. 哪些适合写进 CLAUDE.md？哪些适合做成 Skills？ 3. 有没有适合用 Hooks 的操作？需要 MCP 吗？

Claude 的分析结果（你期望看到）：

需求推荐工具理由
项目目标、输出格式规范、文件命名规则 CLAUDE.md 每次都要遵守，放这里省得每次说
小红书文案风格、配图 prompt 格式 Skills 只在生成小红书内容时才需要，不必常驻 context
HTML 笔记写完后自动格式化 Hooks 机械动作，必须每次执行，不能漏
HTML 内容完成后做质量审查 Subagent 需要 fresh eyes，隔离审查过程不污染主对话
读取外部服务数据 不需要 MCP 所有输入都在本地文件里，无需连接外部服务
Explore 阶段的核心价值：在还没写一行配置之前，就把工具选型想清楚。后面的所有工作都在这个框架下进行，而不是走一步看一步。
✓ 完成信号：你知道要用哪些工具，以及每个工具负责什么
阶段二

Plan — 设计配置方案，零代价纠偏

仍然在 Plan Mode。把 Explore 阶段的选型决策变成具体的配置设计——不是"要用 Skills"，而是"Skills 里放什么内容、文件怎么组织"。这是纠偏代价最低的时机，现在改方向不需要删文件。

CLAUDE.md 设计

这个 workflow 的 CLAUDE.md 只放"每次都要遵守的事"：

# CLAUDE.md（学习笔记 Workflow 项目） ## 项目目标 将学习资料整合成 HTML 学习笔记 + 小红书内容包。 ## 输入文件位置 - 学习资料：消化/{日期}/ - 已有笔记：输出/{日期}/ ## 输出规范 - HTML 笔记：输出/{日期}/claude-code-notes-{N}.html - 小红书文案：输出/{日期}/{N}-小红书文案.md ## 内容原则 - 按知识脉络组织，不按课程顺序 - 不重复解释概念，只给新视角 - 同一 CSS 风格（参见 notes-I.html 的设计令牌） ## 禁止操作 - 不修改已有的笔记文件 - 不自行决定输出目录，总是用今天的日期 @style-guide.md # CSS 变量和卡片类型说明

Skills 设计

两个 Skills，各司其职：

skills/ ├── xiaohongshu/ │ └── SKILL.md # 小红书文案风格 + 写作流程 └── image-prompt/ └── SKILL.md # 配图 prompt 格式规范 --- xiaohongshu/SKILL.md 的结构 --- --- name: xiaohongshu description: 生成小红书文案，包含心路历程写法和引发共鸣的风格 --- ## 文案风格原则 - 真实学习过程，不是固定模板 - 问题驱动：遇到问题 → 钻研 → 发现解决方案 - 不要 AI 味，不要营销号 ## 参考结构（灵活使用，不要照搬） 开头：最近在学 Claude Code，今天学到 xxx 核心概念：2–3 个关键点 心路历程：想到我遇到过 xxx 问题... 结尾：完整笔记在评论区 👇

Hooks 配置

一个 Hook 解决一个"每次都必须做但经常会漏"的操作：

// settings.json 里的 Hooks 配置 { "hooks": { "PostToolUse": [ { "matcher": "Write|Edit", "hooks": [ { "type": "command", "command": "prettier --write \"$CLAUDE_FILE_PATH\" 2>/dev/null || true", "description": "HTML 文件写完后自动格式化" } ] } ], "Stop": [ { "hooks": [ { "type": "command", "command": "osascript -e 'display notification \"任务完成\" with title \"Claude Code\"", "description": "任务完成后发桌面通知" } ] } ] } }

Subagent 配置设计

HTML 笔记写完后，用一个只读的 Reviewer Subagent 检查内容质量——它看不到写作过程，只评价最终结果：

--- .claude/agents/note-reviewer.md --- name: note-reviewer description: 审查 HTML 学习笔记的内容质量 tools: Read, Glob # 只读权限，不能修改 model: haiku # 审查任务用轻量模型 memory: project # project scope，跨 session 积累审查经验 --- 你是一个学习笔记质量审查员。审查要点： 1. 先查阅 memory，了解本项目的历史问题 2. 检查：结构是否清晰、有没有重复解释前三篇已有概念、 CSS 风格是否一致、模块四篇幅是否占 40%+ 3. 审查后更新 memory，记录新发现的问题类型
注意 MCP 的缺席：这个 workflow 不需要 MCP，因为所有输入都在本地文件里。如果未来需要从 Notion 读取课程大纲、或者把笔记发布到某个平台，那时候再加 MCP。工具是按需引入的，不是因为"能用"就提前加。
✓ 完成信号：每个工具放什么、文件怎么组织，方案已经确定，你审阅过并同意
阶段三

Code — 把方案变成真实配置

方案批准后，切换到 Default 模式，按顺序把每一份配置文件建起来。顺序很重要：先建 CLAUDE.md，让 Claude 知道项目背景；再建 Skills，建 Hooks，最后建 Subagent。

1
用 /init 生成 CLAUDE.md 基础，再手动补充

在项目目录下运行 /init，Claude 会扫描代码库自动生成一份基础 CLAUDE.md（技术栈、文件结构）。然后手动追加你在 Plan 阶段设计的内容规范和禁止操作。
技巧：不要从头手写，/init 帮你把"已经能看出来的信息"写完，你只补"看不出来的隐性规则"。

2
创建 Skills 文件

建立 skills/xiaohongshu/SKILL.md 和 skills/image-prompt/SKILL.md，填入 Plan 阶段设计好的内容。写完后让 Claude 验证：你能调用 xiaohongshu 这个 Skill 吗？——它应该能从目录里找到并描述这个 Skill。

3
配置 Hooks

在 .claude/settings.json 里写入 PostToolUse 和 Stop 两个 Hook。配置完成后做个测试：让 Claude 写一个小 HTML 文件，确认保存后自动触发了格式化（不要信"应该生效了"，要真的看一眼文件）。

4
创建 Subagent 配置

建立 .claude/agents/note-reviewer.md，填入 Plan 阶段设计的配置。让 Claude 调用一次：用 note-reviewer 审查最近这篇笔记，验证它能正常启动并返回审查意见。

5
端到端跑一次

用一份真实的学习资料，完整跑一遍 workflow：
读入资料 → 生成 HTML 笔记 → Hooks 自动格式化 → Subagent 审查 → 生成小红书内容（调用 xiaohongshu Skill）。
检查：每个工具都用到了吗？输出格式符合规范吗？有没有哪步需要手动介入？

搭建顺序的逻辑：先 CLAUDE.md → 后其他工具。因为 Skills、Subagent 的 prompt 里可能引用项目规范，如果 CLAUDE.md 还没建好，Claude 在后续步骤里就没有稳定的"地基"，会产生不一致。
✓ 完成信号：端到端跑通一次，每个工具都实际参与了工作
阶段四

使用中的记忆管理 — 让系统越用越懂你

Workflow 建好了，但它不会在第一天就达到最佳状态。这一阶段描述的是使用过程中会发生的事——不需要你主动干预，系统在悄悄进化。

什么时候发生了什么你需要做什么
第一次跑完 Auto Memory 开始积累你的偏好，比如你纠正了输出格式，Claude 记下来了 什么都不用做，观察 Memory 文件是否有新内容
长任务进行中 Context Window 使用率升高，Claude 开始读入多份资料文件 运行 /context 查看使用率，超过 60% 考虑 /compact
Reviewer 跑了几次后 Persistent Memory 里积累了"这个项目常见的笔记问题"，Reviewer 审查越来越准 偶尔打开 .claude/agent-memory/note-reviewer/ 看看它记了什么
发现某条 CLAUDE.md 规则总被忽略 Claude 理解规则但执行不一致——这条规则可能更适合 Hook 把这条规则从 CLAUDE.md 移到 Hooks 配置里
跑了几十次 session 后 Dream Agent 自动整理 Memory，合并重复条目，维持在 200 行以内 什么都不用做，Dream Agent 在后台处理

Context 使用的经验规律

// 学习笔记 workflow 的典型 context 分布 启动时（什么都没做）： System prompt ~5% CLAUDE.md ~2% Skills 目录索引 ~1% ──────────────────────────── 已用 ~8%，剩余 ~92% 读入一份课程 Markdown + 三篇已有笔记： + 文件内容 ~15-20% ──────────────────────────── 已用 ~25-30% 生成 HTML 笔记过程中（多轮工具调用）： + 对话历史 ~10-20% ──────────────────────────── 已用 ~40-50%（这时候可以考虑 /compact） 如果还要继续生成小红书内容： + xiaohongshu Skill ~1%（按需加载） + 继续对话 ~10%+ ──────────────────────────── → 超过 70% 时强烈建议 /compact 一次
✓ 完成信号：用了几次之后，Claude 的行为越来越符合你的期望，纠正次数越来越少
阶段五

遇到问题怎么处理 — Troubleshooting Guide

真实使用中一定会遇到问题。大多数问题都有固定的"症状 → 诊断 → 修复"路径：

症状根本原因修复方法
Claude 开始忘事，重复已解决的问题，或者行为偏离规范 Context Window 被压缩，早期内容丢失 运行 /context 确认，用 /compact 压缩；若是跨 session 遗忘，检查 CLAUDE.md 和 Memory 是否完整
Claude 反复犯同一个错误（比如总用错文件命名格式） 规则在 CLAUDE.md 里写了，但 Claude 没有一致执行 把这条规则写得更具体、更靠前；如果是机械操作，改用 Hook 强制执行
某个格式化或通知操作时不时漏掉 把"必做操作"写进了 CLAUDE.md，依赖 Claude 自觉 把这个操作移到 Hooks（PostToolUse 或 Stop），用确定性代替概率性
Reviewer Subagent 不知道项目历史，每次从头来 Subagent 配置里没有开启 Persistent Memory 在 note-reviewer.md 的 frontmatter 里加 memory: project
Context 刚启动就用了很多，还没开始工作就很紧张 MCP 工具定义全量加载，或 Skills 目录太大 用 /mcp 关掉这次不用的 MCP 服务器；清理掉不再使用的 Skills
Hooks 配置了但没有生效 settings.json 路径不对，或 matcher 写法有误 用 /hooks 命令查看当前已加载的 hooks；检查 matcher 是否匹配了正确的工具名
xiaohongshu Skill 生成的文案有 AI 味 Skill 里的风格描述太抽象，没有负面示例 在 Skill 里补充"❌ 不要这样写"的具体示例，以及你觉得好的真实文案作为参考
排查问题的通用思路：遇到 Claude 行为不符合预期时，先问两个问题——①它是真的不知道（信息没传进去），还是知道但没做（执行问题）？ 如果是前者，检查 CLAUDE.md / Memory / Skills 是否到位；如果是后者，考虑是否需要把这条规则从"自然语言提示"升级为"Hook 强制执行"。
✓ 完成信号：遇到问题能快速定位原因，知道该动哪个配置文件
模块五

写给未来的自己 — 持续迭代的心态

到这里，你已经有了全景地图、辨析清单、决策框架，也跑通了一个真实的 workflow。但有一件事比所有配置都重要：这套系统是活的，不是一次搭完就万事大吉的。

每个工具都有自己的"生长方式"

📄
CLAUDE.md 不是一次写完的

第一天可能只有三行。随着你发现 Claude 反复犯同一个错误、做了你不想要的假设，你才知道应该补什么规则。好的 CLAUDE.md 是从实践里"长出来的"，不是凭空设计出来的。它的演化轨迹就是你和这个工具磨合的历史。

🧠
Memory 不是你维护的

Auto Memory 是 Claude 替你维护的。你不需要时刻想着"这件事要不要记下来"——Claude 在工作中会自己判断。你需要做的只是偶尔检查 Memory 文件，确认它记的方向是对的，发现过时的条目时手动清理。这是一种新的分工：你负责把关，它负责积累。

🪝
Hooks 不是一开始就配齐的

第一次搭 workflow 的时候，你不一定知道哪些操作"总是漏"。Hooks 是在你发现了问题之后才加的——当你第三次因为忘了格式化而烦恼，才是真正应该写 Hook 的时机。提前把所有可能的 Hook 都配上，反而会制造噪音。

🔧
Skills 和 MCP 是按需叠加的

今天的 workflow 只需要本地文件，所以不需要 MCP。如果有一天你想从 Notion 里读取课程大纲、或者把生成的内容直接发布出去，那时候再加 MCP。Skills 也一样——先用最简单的方式完成任务，当某类任务开始频繁出现且方法稳定下来，再把它封装成 Skill。

一张系统成熟度示意图

// 典型的 workflow 演化路径 第 1 天 CLAUDE.md（3行） ↓ 发现 Claude 用了错误的文件命名 第 3 天 CLAUDE.md（补充文件命名规范） ↓ 发现格式化总是漏 第 7 天 + Hooks（PostToolUse 自动格式化） ↓ 小红书内容任务开始频繁出现 第 14 天 + Skills（xiaohongshu / image-prompt） ↓ 想要更客观的质量审查 第 30 天 + Subagent（note-reviewer，开启 Persistent Memory） ↓ 持续使用，Memory 悄悄在积累 持续 Auto Memory 越来越懂你 Reviewer 越来越准，Persistent Memory 在积累 CLAUDE.md 随着新问题的出现持续补充 整个系统越来越像你专属的 AI 搭档
为什么这张图很重要：注意每一步都是"发现问题 → 升级工具"，而不是"提前想好所有场景 → 一次配齐"。试图在第一天就搭出完美配置，往往会配出一堆用不上的复杂性。最好的起点是最简单的可以工作的版本，然后让真实使用告诉你哪里需要加强。

真正让 Claude 成为专属助手的，不是配置文件

工具是死的，用法是活的。CLAUDE.md 只是一个文件，Skills 只是一堆 Markdown，Hooks 只是一些 shell 命令——它们本身没有任何魔力。

真正让这套系统有价值的，是你在使用过程中不断观察、调整、补充的行为：你发现 Claude 做错了就纠正，Claude 学到了就记下来；你发现某件事总是漏就加 Hook，发现某个方法可以复用就封装成 Skill。每一次这样的迭代，系统就更懂你一点。

这不是一个可以"配置完成"的系统，而是一个随着你们合作深入而持续进化的关系。一年后你的 CLAUDE.md，会比今天的版本精准得多——不是因为你更懂工具了，而是因为你们一起工作了一年。

一句话收尾：
工具是死的，用法是活的。真正让 Claude 成为你的专属助手的，不是配置文件，而是你和它一起工作的过程。
