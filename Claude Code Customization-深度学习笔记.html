Context Window — 工作记忆的本质

学习 Claude Code 一段时间后，你一定遇到过"Claude 开始偏离方向"或"它好像忘了之前说的"这种情况。这不是玄学，而是 Context Window 被填满了。理解这个机制，是做好深度定制的基础。

💡 Context Window 的真实构成

很多人以为 Context Window 只装"对话历史"。其实它装的东西比想象中多得多：

  • 对话历史（~30%）：你说的话 + Claude 的回复
  • 读取的文件内容（~25%）：每次 view 一个文件都占空间
  • 命令执行结果（~20%）：bash 命令的输出也要存储
  • MCP 工具定义（~10%）：连接的外部服务描述
  • Skills 目录（~5%）：加载的技能名称和描述
  • System prompt（~3%）：内置指令

三个关键命令

命令作用用法场景效果
/context查看 Context 使用情况感觉 Claude 变慢时检查可视化各类别占用
/compact压缩历史，保留记忆继续当前任务但快到上限了释放空间，保留核心
/clear完全清空，不保留历史开始全新任务时重置所有 Context
📊 实测数据：刚启动就用了 7%

我在 learning-workflow 目录刚启动 Claude，立刻运行 /context，发现 context 已经用了 7%：

claude-sonnet-4-6
13k/200k tokens (7%)

Estimated usage:
- System prompt:  1.4k tokens (0.7%)
- System tools:   7.0k tokens (3.5%)  ← 最大头！固定成本
- MCP tools:     0.46k tokens (0.2%)  ← 空转中
- Custom agents:  0.31k tokens (0.2%)
- Skills:         2.5k tokens (1.3%)  ← 加载了 lark 系列但不用
- Messages:       1.4k tokens (0.7%)

结论：1.5% 是 Skills 和 MCP 在占空间但没干活。Context 管理不只是"满了才处理"，要主动优化工具加载。

/clear 与 CLAUDE.md 的黄金搭档

/clear 的问题是清空后什么都不记得了，但 CLAUDE.md 的内容每次启动都会重新加载。所以正确的工作节奏是：

  1. 一个功能做完，把这次学到的规则、偏好补充到 CLAUDE.md
  2. 运行 /clear 清空 Context，得到全新起点
  3. 下次启动，Claude 自动读取 CLAUDE.md，不需要重新解释
💡 Subagent 解决"探索性任务污染主 Context"

有时候你需要让 Claude 去探索一个大型 codebase，但探索过程会产生大量"中间过程"污染 Context。解决方案：用 Subagent 做探索性任务，它只返回 summary，不污染主 Context。这是 Subagent 的核心价值之一，在第六章会详细讲。

持久化记忆 — 让 Claude 跨 Session 记住项目

LLM 是无状态的——每次 API 调用都是全新实例，Session 结束后所有上下文消失。持久化记忆就是解决这个根本矛盾的机制。Claude Code 提供了三套并行的持久化机制，各司其职。

CLAUDE.md — 项目的"提前写好的 prompt"

CLAUDE.md 本质上就是预设的 system prompt，每次启动时自动追加到你的 prompt 里。它只有一个特殊功能：Claude Code 启动时自动读取，仅此而已。

没有 CLAUDE.md 的日常

你：帮我写一个 React 组件
Claude：用哪个框架？什么风格？
你：Next.js 15，Tailwind

[第二天]
你：再写一个组件
Claude：用哪个框架？什么风格？
你：😤 昨天不是说了吗！

有 CLAUDE.md 的日常

# CLAUDE.md
## 技术栈
- Next.js 15
- Tailwind CSS
- pnpm 包管理器

## 代码规范
- 2 空格缩进
- TypeScript 严格模式

[每次启动自动加载，不用再解释]
💡 @ 引用：保持 CLAUDE.md 简洁的诀窍

复杂项目的 CLAUDE.md 可以只做"目录"，用 @ 引用具体的规范文件：

# CLAUDE.md
@workflow-rules.md       ← 生成笔记的规范
@output-format.md        ← 输出格式标准
@xiaohongshu-style.md    ← 小红书文案风格
@我的学习方式-AI辅助学习指南.md

这样既保持 CLAUDE.md 简洁，又能让每个规范文件独立维护，Git 追踪也更清晰。

📌 CLAUDE.md 的演化过程：从实践倒推

最佳实践不是"一开始想象所有规则"，而是遇到问题 → 纠正 → 记录 → 下次不犯：

时间遇到问题补充到 CLAUDE.md
第 1 天Claude 不知道用哪个框架## 技术栈: Next.js 15
第 3 天Claude 总用 npm，我用 pnpm## 命令: pnpm install
第 7 天Claude 总写 API routes## 规范: 优先 server actions
第 14 天缩进风格不一致## 代码规范: 2 空格缩进

例外：固定流程项目（如 workflow 自动化脚本）可以提前把规则全部写进去，因为目标明确、流程固定。

Persistent Memory — Subagent 的跨 Session 专家记忆

如果说 CLAUDE.md 是你手动维护的规则文档，那 Persistent Memory 就是 Subagent 在工作过程中自己积累的经验。它有三种作用域：

Scope存储路径可 Git 共享适用场景
user~/.claude/agent-memory/❌跨项目通用知识
project.claude/agent-memory/✅ 推荐团队共享 reviewer 记忆
local.claude/agent-memory-local/❌不想提交的私有知识

MEMORY.md 的架构设计：两层结构

.claude/agent-memory/code-reviewer/
├── MEMORY.md           ← 索引文件（≤200行，启动时自动注入）
│   [auth] JWT 必须用 UTC+0，本地时区导致验证失败 → auth-patterns.md
│   [perf] N+1 查询已出现 3 次，重点检查 ORM 调用 → perf-issues.md
│   [debt] auth/legacy.ts 有 5 个未处理 TODO → tech-debt.md
├── auth-patterns.md    ← topic 文件（Agent 按需读取，不限大小）
├── perf-issues.md
└── tech-debt.md

MEMORY.md 前 200 行在启动时自动注入 system prompt，超出部分 Agent 可以主动读取。这是刻意的工程权衡：200 行约 3000~5000 tokens，平衡"有用背景知识"和"不拖累 context window"。

💡 Dream Agent：自动整理 Memory 的后台管家

当 MEMORY.md 超出 200 行时，Dream Agent 会自动触发（距上次整理 24h 且有 5 个新 session），做以下工作：

  • 合并重叠条目，删除过时内容
  • 把详细内容移入 topic 文件
  • 维持 MEMORY.md 在 200 行以内

你也可以手动输入 dream

Skills — 按需加载的插件化知识系统

如果说 CLAUDE.md 是"每次都要记住的规则"，那 Skills 就是"需要时才拿出来的专业手册"。它的设计哲学非常优雅：让 Agent 知道有什么能力，但不让无关知识永远占据 Context。

两层加载模型：发现 vs 掌握

🎯 Skills 的核心价值：85% token 节省
方式10个 Skills 的成本说明
传统方式（全放 System Prompt）10 × 2000 = 20,000 tokens所有知识永远在 Context
Skills 方式10 × 100 + 1 × 2000 = 3,000 tokens只加载目录 + 需要那一个
节省↓ 85%每次 API 调用省 17,000 tokens

Skill 的文件结构

---
name: xiaohongshu-casual
description: 口语感悟风的小红书文案，适合记录学习心路历程
---

## 文案风格
真实的学习过程，不是固定模板。开头引出最近学到的有趣事，
核心概念列举2-3个关键洞察，中间穿插遇到的困惑和解答，
结尾自然收束。

## 禁止
- 不要 AI 味、营销号腔
- 不要"总结一下就是"这种套话

YAML frontmatter（---之间）里的 name 和 description 是 Layer 1 的内容，其余部分是 Layer 2 的内容。两层分离，各司其职。

CLAUDE.md vs Skills：清晰的分工

CLAUDE.md：核心任务流程（What）

你的任务：
1. 读取学习材料
2. 生成学习笔记
3. 调用 xiaohongshu skill
4. 调用 image-prompt skill

Skills：执行细节（How）

skills/
├── xiaohongshu-casual/
│   └── SKILL.md  ← 口语风格规范
├── xiaohongshu-professional/
│   └── SKILL.md  ← 专业知识风
└── sd-image-prompt/
    └── SKILL.md  ← 配图 prompt 模板
💡 这是从"学会工具"到"理解系统设计"的关键跃迁

Skills 不只是"提示词工程"，它体现了一个设计原则：知识在需要的 moment 才进入上下文，不该永远占据 System Prompt。掌握这个思路，才能真正设计出高效的 AI 工作流。

MCP — 连接外部世界的协议桥梁

Claude Code 本身只能访问你的本地代码文件，但实际工作中的数据散落在各处：Linear 的任务、Notion 的文档、数据库的用户数据……MCP（Model Context Protocol）就是连接这些外部工具的协议标准。

HTTP 服务器

由服务商托管，通过网络连接

  • Linear、Jira（任务管理）
  • Context7（最新技术文档）
  • Notion、Google Drive

Stdio 服务器

在本地运行的进程

  • 本地数据库连接
  • 自定义 Python 脚本
  • 内部 API 服务

MCP 的三种作用域

Scope配置位置共享范围
Local本机配置只有你，当前项目
User用户配置只有你，所有项目
Project.mcp.json团队共享 ✅
⚠️ MCP 的 Context 成本
MCP 服务器会将所有工具定义加载到 Context Window，即使不使用也会占用空间（不像 Skills 只加载目录）。所以要养成习惯：用 /mcp 定期检查已连接的服务器，禁用不常用的。如果工具定义超过 Context 的 10%，Claude Code 会自动切换到 tool search 模式。
💡 我的 workflow 当前不需要 MCP

判断是否需要 MCP 的标准很简单：数据在本地还是外部？

  • 学习资料是本地 markdown 文件 → 不需要 MCP
  • GitHub 操作 → Git 命令就够了
  • 小红书发布 → 目前手动更简单

何时需要：从 Notion 读笔记 → Notion MCP；查最新 API 文档 → Context7 MCP。按需接入，不要为了用而用。

Hooks — 确定性执行机制

你有没有在 CLAUDE.md 里写过"每次修改代码后运行格式化"？大部分时候 Claude 会做，但有时候会忘。Hooks 解决的正是这个问题：把"可能会做"变成"100% 一定做"。

❌ 提示方式（不确定）

在 CLAUDE.md 写：
"每次编辑文件后运行 Prettier 格式化"

⚠️ 大部分时候会做
⚠️ 但有时候会忘记

✅ Hooks 方式（确定）

settings.json 配置：
PostToolUse + 匹配 Edit|Write
→ 自动运行 prettier --write

✓ 100% 执行，无例外
✓ Claude 没有选择权

五个生命周期事件

Hook 类型触发时机能否阻止操作典型用途
PreToolUse工具执行前✅ 可以（exit code 1）安全检查、权限验证
PostToolUse工具执行后❌ 不能自动格式化、日志记录
UserPromptSubmit用户提交时✅ 可以输入验证、注入上下文
StopClaude 完成回复-发送完成通知、自动提交
Notify通知事件-桌面推送

退出码协议

Exit Code含义PreToolUse 效果PostToolUse 效果
0成功继续执行工具正常继续
1阻止工具不执行，stderr 作为错误返回警告日志
2注入消息stderr 注入对话，工具仍执行stderr 追加到结果

决策框架：Hook 还是 CLAUDE.md？

判断维度→ Hook→ CLAUDE.md
能用"每次 X 就 Y"一句话说清✅❌
需要"看情况而定"❌✅
需要理解文件内容❌✅
机械重复的动作✅❌
需要创造性判断❌✅

Hooks 配置示例

// settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "prettier --write $HOOK_TOOL_INPUT_PATH --parser markdown"
          }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "./scripts/check-dangerous.sh"
          }
        ]
      }
    ]
  }
}
💡 "机器人做机械工作，助手做智能工作"

Hook 就像工厂流水线上的机器人：看到动作类型（Write/Edit），运行简单命令，机械地 100% 执行。它不能理解文件内容，不能判断"写完了吗"，不能做创造性工作。Claude 是有经验的助手：能理解意图、判断完成度、做创造性生成，但可能偶尔会忘记某个步骤。两者结合，才是最佳工作流。

Subagents — 隔离、并行与独立视角

Subagent 最容易被误解为"主 Agent 的一部分"。实际上，Subagent 是完整的独立 Claude 实例，有自己独立的 Context Window 和 messages 数组。主 Agent 的历史对话它完全看不到。

主 Agent                          Subagent
+-----------------------------+   +---------------------+
| messages = [                |   | messages = [        |
|   历史对话（1000条）          |   |   task prompt       |
|   工具调用结果（500个）        | → | ]                   |
|   读取的文件（50个）           |   |                     |
|   几万 tokens               |   | 几百 tokens（干净！）  |
| ]                           |   |                     |
+-----------------------------+   +---------------------+
         |                                  |
         |                             执行任务
         |                             生成 summary
         |        只返回 summary        |
         | <-------------------------------+
         |
    context 保持干净

三种核心应用场景

🔍 场景A：Code Review — 独立视角，避免认知偏差

主 Agent 写完代码后，它"知道"自己想做什么，所以可能看不到 bug。Subagent 没有这个先入之见，只看"代码实际做了什么"。

之前的方式（低效）

  1. 遇到问题
  2. 打开全新 Agent 窗口
  3. 手动复制代码
  4. 重新解释 context 和问题

费时、容易遗漏信息

Subagent 方式（高效）

  1. 主 Agent 写完代码
  2. 调用 Subagent reviewer
  3. Subagent 自动读取文件
  4. 返回客观审查结果

快速、完整、有 fresh eyes

💡 权责分离原则在 Agent 世界的体现

就像公司里开发 ≠ QA，运动员 ≠ 裁判。Code writer（主 Agent）用 edit 权限，Code reviewer（Subagent）用 read-only tools。"A reviewer should flag issues, not edit files"。

Reviewer Subagent 配置示例：

---
name: code-reviewer
description: 审查代码质量，检查 bug、安全问题和最佳实践
tools: Read, Glob, Grep
model: haiku
memory: project
---

你是代码审查专家。审查时：
1. 先查阅 memory，了解项目历史问题
2. 针对本次变更进行客观审查
3. 审查完成后更新 memory，记录新发现
⚡ 场景B：并行任务 — 多模块同时开发，互不干扰 
主 Agent（Project Leader）
├── Subagent 1: 前端组件开发  → context A
├── Subagent 2: 后端 API 开发 → context B
├── Subagent 3: 数据库 schema → context C
└── 主 Agent 整合所有结果

三个 Subagent 可以并行工作，各自的探索过程互不干扰，最终只把结果汇报给主 Agent。

🔬 场景C：临时研究 — 脏活不污染主线

开发过程中遇到"这个库怎么用"，如果让主 Agent 去探索，会大量消耗 Context。用 Subagent 研究，只返回"最终答案"，主 Context 保持干净。

主 Agent 在开发核心功能
  ↓
遇到问题："Zod v3 的类型推导怎么用？"
  ↓
Subagent：查文档 → 读源码 → 实验代码 → 返回"用法摘要"
  ↓
主 Agent 继续开发（Context 几乎没变）

Preload Skills：Subagent 的特殊之处

主 Agent 里的 Skills 是"按需加载"，而 Subagent 配置里可以指定 skill: [docx, pdf]，这些 Skill 的完整内容会被预加载，而不是"等用到才加载"。原因：Subagent 生命周期短，预加载让它立刻具备完整能力。

🎯 Subagent 的核心价值：Context Boundary
  • 不是"Agent 的一部分"，是完整独立的 Claude 实例
  • 核心价值 = Context Boundary：探索过程不污染主 Agent
  • 主 Agent 只接收 summary，不是完整的操作历史
  • Persistent Memory（project scope）可让 Subagent 跨 Session 积累经验

搭建每日学习内容消化输出的自动化 Workflow

本章所有知识——Context 管理、CLAUDE.md、Skills、MCP、Hooks、Subagents——都是为了同一个目标服务的工具。这一节用分析过程 + 实践步骤，把这些工具组合成一个完整的自动化 workflow。

需求分析

Workflow 目标

输入：
  消化/ 目录下的
  ├── 每节课学习笔记（HTML）
  └── 学习资料（markdown + 图片）

输出：
  输出/ 目录下的
  ├── 章总结-{主题}-深度学习笔记.html （本文这样的）
  └── {章节号}-小红书内容包/
      ├── 文案.md
      └── 图片prompt.md

工具选型分析

在动手之前，先用本章学到的决策框架，分析每个任务应该用什么工具：

任务需要智能判断？每次都执行？选择理由
读取并整合学习笔记✅ 是❌ 指定时才做CLAUDE.md需要理解内容脉络
生成章总结 HTML✅ 是❌ 指定时才做CLAUDE.md需要按知识脉络重组
小红书文案风格规范--Skills可复用的"怎么做"，按需加载
配图 prompt 模板--Skills可复用，贴纸风格固定规范
markdown 自动格式化❌ 不需要✅ 每次写文件Hook"每次写 md 就格式化" 一句话能说清
完成后 Git 提交❌ 不需要可选Hook（Stop）机械操作，不需要智能判断
审查 workflow 代码质量✅ 是❌ 按需Subagent需要 fresh eyes，避免认知偏差
连接外部服务--MCP（暂不需要）数据都在本地，MCP 引入的 Context 成本不值得
💡 分析结论：CLAUDE.md + Skills + Hooks 是核心组合

不是每种工具都必须用。MCP 当前不需要，Subagent 只在审查 workflow 代码时需要，主要工作靠 CLAUDE.md（定义流程）+ Skills（定义风格）+ Hooks（确保机械操作不遗漏）。

实践路线

Phase 1 环境搭建与基础配置 第 1 天完成
分析思路： 首先要有结构清晰的项目目录，然后写 CLAUDE.md 让 Claude 知道项目是什么、规范在哪里。配一个最简单的 Hook（markdown 自动格式化）验证 Hooks 机制可以工作。
  1. 创建项目文件夹结构 
    D:/BUILD MYSELF/Anthropic courses/
├── 消化/                    ← 每日学习资料存放
│   └── YYYY-MM-DD/
│       ├── 2.x.x-xxx-学习笔记.html
│       └── impressive points.md
├── 输出/                    ← 生成的内容存放
│   └── YYYY-MM-DD/
│       ├── 章总结-{主题}-深度学习笔记.html
│       └── 小红书内容包/
├── 规范/                    ← 规范文件目录
│   ├── output-format.md     ← 章总结 HTML 规范
│   ├── xiaohongshu-style.md ← 小红书文案风格
│   └── workflow-rules.md    ← 工作流程规则

Phase 4 自动化触发：Hooks 扩展 第 6-7 天完成
分析思路： 手动流程稳定后，再考虑用 Hooks 自动化机械部分。Stop Hook 可以在 Claude 完成任务后自动做 Git 提交。注意：生成内容的质量检查仍需人工，不要过度自动化。
  1. 添加 Stop Hook：完成后自动 Git 提交 
    // .claude/settings.json 更新
{
  "hooks": {
    "PostToolUse": [...之前的格式化 hook...],
    "Stop": [
      {
        "hooks": [{
          "type": "command",
          "command": "cd 'D:/BUILD MYSELF/Anthropic courses' && git add 输出/ && git status"
        }]
      }
    ]
  }
}

    注意：只 git add，不自动 commit，保留人工审查 → 手动 commit 的环节。

exit 0

分析思路： 当 workflow 脚本（规范文件 + Hooks 脚本）有一定规模后，用 Subagent 做代码审查。这时 Subagent 的"独立视角"价值才能发挥——它不受"我写的所以是对的"的认知惯性影响。

🎯 核心设计原则回顾
工具在本 Workflow 的角色判断依据
CLAUDE.md定义"做什么"的核心流程需要智能判断的任务
Skills封装文案风格等可复用的"怎么做"独立、可复用、按需加载

Subagent代码质量审查、独立视角需要 fresh eyes，不受认知惯性影响
