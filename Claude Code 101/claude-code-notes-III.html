Claude Code 学习笔记 III

五大定制工具，从给 Claude 写说明书到连接外部世界
模块一

CLAUDE.md — 给 Claude 的项目说明书

每次打开 Claude Code，它对你的项目一无所知。你用什么框架、遵循什么规范、哪些命令不能乱跑——它都不记得。CLAUDE.md 就是解决这个问题的工具。

1.1　没有 CLAUDE.md 的痛苦

想象两个真实场景：

// 场景一：每次都要重新解释 你：帮我写一个组件 Claude：用哪个框架？什么风格？ 你：Next.js 15，Tailwind，上次说过的！ // 第二天重开会话 你：再写一个组件 Claude：用哪个框架？什么风格？ 你：😤
// 场景二：Claude 做错误假设 你的项目用 pnpm ↓ Claude 假设你用 npm ↓ Claude: npm install xxx 你：不对，我们用 pnpm！ ↓ 反复纠正，浪费时间

这两个问题的根源是一样的：Claude 没有项目背景知识，每次会话都从零开始。

1.2　CLAUDE.md 的本质：提前写好的 prompt

CLAUDE.md 没有任何魔法。它的唯一特殊之处只有一条：

启动 Claude Code 时，自动读取 CLAUDE.md，把内容追加到你的 prompt。
就这一点，仅此而已。其他方面它和普通 Markdown 文件没有区别。

理解了这一点，很多问题就迎刃而解：为什么 CLAUDE.md 里写的规则会生效？因为它们在每次对话开始前就已经进入了 Claude 的上下文，相当于你每次都在开头说了一遍。

启动 Claude Code ↓ 自动读取 CLAUDE.md ↓ 内容追加到 System Prompt ↓ Claude 已经知道：框架、工具、规范、命令 ↓ 你直接说任务，不用再解释背景

1.3　@ 引用语法：保持主文件简洁

随着项目变大，规则越来越多，全塞进一个 CLAUDE.md 会很难维护。@ 引用语法解决这个问题：

# CLAUDE.md（只有目录，保持简洁） @workflow-rules.md @output-format.md @style-guide.md

Claude 启动时读到 @workflow-rules.md，会自动去读那个文件的内容，效果等同于把内容直接写在 CLAUDE.md 里。好处是：

  • CLAUDE.md 只做索引，一目了然
  • 具体规则分文件管理，各司其职，易于维护
  • Git 追踪更清晰，改了哪个规则文件一眼就看出来

1.4　写什么内容：两种策略

CLAUDE.md 的内容没有固定模板，取决于你的项目类型：

项目类型特点CLAUDE.md 策略
探索性项目 一开始不知道要做什么，摸索中发现需求 从实践倒推——遇到问题、纠正、记录，下次不犯
固定流程项目（如 workflow 脚本） 目标明确，流程固定，规范清晰 提前写规则——完全合理，一次写好长期生效

探索性项目的典型演化过程：

1
第 1 天：项目刚开始

CLAUDE.md 只有一行：# 这是一个 Next.js 项目

2
第 3 天：发现 Claude 总用 npm

补充：安装依赖用 pnpm install，不要用 npm

3
第 7 天：发现 Claude 总写 API routes

补充：优先使用 server actions，不要写 API routes

4
持续迭代

每次遇到问题就记录，CLAUDE.md 越来越精准，Claude 越来越懂你的项目。

核心原则：不是一开始就想象所有规则，而是遇到问题 → 纠正 → 记录 → 下次不犯。CLAUDE.md 是从实践中长出来的，不是凭空设计出来的。

典型内容结构包括：技术栈说明、常用命令、代码规范、需要遵循的规则、用 @ 引用的规范文档。

1.5　Project-level vs User-level：团队共享 vs 个人偏好

类型位置作用范围适合放什么提交 Git
Project-level 项目根目录 整个团队共享 技术栈、团队规范、项目命令 ✅ 是
User-level 用户配置文件夹 只对你生效，跨所有项目 个人偏好、工作习惯、常用工具 ❌ 不要

对于个人项目，两个 level 合二为一。但理解这个概念，将来团队协作时会用到——团队规范放 Project-level 让所有人共享，个人习惯放 User-level 不影响他人。

CLAUDE.md 和 Memory 的分工：CLAUDE.md 是静态规则——技术栈、规范、命令，手动维护，随项目提交 Git；Memory 是动态经验——Claude 从对话中自动积累的记忆，跨 session 保留。前者是你写给 Claude 的说明书，后者是 Claude 自己记的笔记。
可以完全不用 CLAUDE.md 吗？
完全可以。CLAUDE.md 的唯一特殊之处是"启动时自动读取"，如果你不介意每次手动说"先读 workflow-rules.md"，效果是一样的。CLAUDE.md 只是省掉这一步——让规则自动生效，不需要你每次提醒。对于偶尔用一次的任务，不创建 CLAUDE.md 也完全合理。
模块二

Skills — 按需加载的知识插件

CLAUDE.md 解决了"让 Claude 记住项目规则"的问题，但有一个隐患：如果你把所有知识都塞进 CLAUDE.md，它会越来越臃肿，每次对话都要把这些内容全部加载进上下文，成本极高。Skills 是解决这个问题的方案。

2.1　Skills 是什么

Skills 是一套插件式知识系统。每个 Skill 是一个 Markdown 文件，描述 Claude 执行某类任务的具体方法。关键在于：这些知识不是永远占据 System Prompt，而是在 Claude 判断需要时才加载进来。

核心思想：知识在需要的那一刻才进入上下文，而不是永远待在那里占位置。

文件结构很简单：

skills/ ├── web-search/ │ └── SKILL.md # 网页搜索的执行方法 ├── write-doc/ │ └── SKILL.md # 文档写作的执行方法 └── code-review/ └── SKILL.md # 代码审查的执行方法

每个 SKILL.md 文件分两部分：

--- name: web-search description: 网页搜索能力，用于查找最新文档和资料 --- # 以上是 YAML Frontmatter（元数据）——给索引用 # 以下是 body（完整内容）——给执行时用 ## Web Search 使用方法 1. 构建查询关键词 2. 调用搜索 API 3. 筛选相关结果 ...

这种"元数据 + 内容"的分离设计，是 Skills 高效运作的关键——下一节会解释为什么。

2.2　两层加载模型：便宜的发现 + 昂贵的执行

Skills 的核心机制是两层加载，每层的成本和目的完全不同：

1
Layer 1：启动时加载目录（便宜）

Claude Code 启动时，扫描所有 SKILL.md 的 Frontmatter，把每个 Skill 的名称和描述加载进 System Prompt。每个 Skill 只占约 100 tokens。Claude 由此知道"有哪些工具可用"，但还不知道怎么用。

2
Layer 2：按需加载完整内容（昂贵）

当 Claude 判断某个任务需要某个 Skill，才去加载该 Skill 的完整 body，作为工具调用结果注入对话。每个 Skill 完整内容约 2000 tokens。用完即弃，不会一直占着。

Layer 1（System Prompt，启动时）： Skills available: - web-search: 网页搜索能力，用于查找最新文档 ~100 tokens - write-doc: 文档写作能力，生成结构化文档 ~100 tokens - code-review: 代码审查能力，检查质量和安全 ~100 tokens ↓ Claude 判断需要 web-search Layer 2（tool_result，按需注入）： <skill name="web-search"> ## Web Search 使用方法 1. 构建查询关键词 2. 调用搜索 API ...（完整内容） ~2000 tokens </skill>

这个设计带来的成本节省非常显著：

方式10 个 Skills 的成本说明
传统方式（全部写进 CLAUDE.md） 10 × 2000 = 20,000 tokens 所有知识永远在 System Prompt，不管用不用
Skills 方式 10 × 100 + 1 × 2000 = 3,000 tokens 只加载目录 + 当次用到的那一个
节省 ↓ 85% 每次 API 调用省 17,000 tokens

2.3　SkillRegistry：图书馆的索引卡片系统

负责管理所有 Skills 的组件叫 SkillRegistry，可以把它理解成图书馆的索引卡片系统：

  • 图书馆有成千上万本书（Skills），但你不需要把每本书都搬到桌上
  • 索引卡片告诉你"有哪些书、各讲什么"（Layer 1 目录）
  • 需要某本书时，才去书架取来（Layer 2 完整内容）

SkillRegistry 的工作流程：

1
启动时扫描

扫描 skills/ 目录下所有 SKILL.md 文件

2
解析并存储

提取每个文件的 Frontmatter（元数据）和 body（完整内容），保存在内存字典中

3
提供两个接口

describe_available() → 返回所有 Skills 的目录（Layer 1 用）
load_full_text(name) → 返回指定 Skill 的完整内容（Layer 2 用）

YAML Frontmatter 的设计意图——关注点分离：
元数据（name、description）给 SkillRegistry 索引用，决定"Claude 知不知道这个 Skill 存在"；
body 内容给执行时用，决定"Claude 知道怎么用这个 Skill"。
两者分开，各自只在需要时出现，互不干扰。

2.4　Skills 和 CLAUDE.md 的区别

两者都是"给 Claude 的知识"，但定位完全不同：

维度CLAUDE.mdSkills
加载时机 启动时，永远在上下文 按需加载，用完即弃
适合放什么 任务流程——做什么、遵循什么规范 执行细节——具体怎么做某件事
成本 永远占用 context 只在用时付费
典型内容 技术栈、命令、代码规范 可复用的执行方法、工作流程
类比 员工手册（入职就发，随时翻阅） 技能培训手册（需要时才拿出来）
Skills 和直接在 CLAUDE.md 里写指令有什么区别？
本质区别是永远在 context vs 按需加载。写在 CLAUDE.md 里的内容，每次对话都会占用 context 空间，不管这次用不用得到。Skills 只在 Claude 判断需要时才加载完整内容，其余时间只有一行描述（~100 tokens）。如果你有 10 个复杂的执行方法，全写进 CLAUDE.md 会消耗 20,000 tokens；用 Skills 只需 3,000 tokens。对于偶尔用到的知识，Skills 是更经济的选择。
模块三

MCP — 连接外部世界的桥梁

CLAUDE.md 和 Skills 解决的都是"Claude 的内部知识"问题。但真实工作中，数据不只在本地代码里——任务在 Linear，文档在 Notion，数据在数据库。Claude Code 本身无法触达这些地方，MCP 就是打通这道墙的协议。

3.1　为什么需要 MCP

Claude Code 默认只能访问你本地的代码文件。但实际工作中的数据散落在各处：

任务管理
Linear、Jira 里的 ticket 详情——"MEN-12 这个任务要做什么？"
技术文档
最新的库文档、API 文档——"shadcn/ui 最新版怎么用？"
数据库
用户数据、业务数据——"users 表有哪些字段？"
协作工具
Notion、Google Drive 里的文档——"这个需求的背景是什么？"
判断是否需要 MCP 的核心问题：你需要的数据在本地吗？
在本地 → 不需要 MCP，Claude Code 直接读文件即可。
不在本地（在外部服务、数据库、云端）→ 需要 MCP 来连接。

3.2　MCP 是什么，两种连接方式

MCP 全称 Model Context Protocol，是一套连接外部工具的协议标准。你可以把它理解成：电话本（知道有哪些外部服务）+ 电话线（实际建立连接的通道）。

有两种连接方式：

类型运行位置连接方式典型例子
HTTP 服务器 由服务商托管，运行在云端 通过网络连接 Linear、Context7、Notion 等第三方服务
Stdio 服务器 在你本地运行的进程 通过标准输入输出通信 本地 Python 脚本、数据库连接工具
Claude Code ↓ 需要外部数据时 MCP 协议（桥梁） ↓ 根据类型选择连接方式 ┌─────────────────┬──────────────────┬─────────────────┐ │ Linear (HTTP) │ Context7 (HTTP) │ 本地DB (Stdio) │ │ 读取 ticket │ 查最新文档 │ 查询数据表 │ └─────────────────┴──────────────────┴─────────────────┘

3.3　三种作用域

MCP 服务器的配置有三个作用域，决定谁能用、在哪里用：

1
Local（本地）

只在当前项目可用，只有你自己能用。适合临时测试或个人专属的连接。

2
User（用户）

你的所有项目都能用，但只对你生效。适合个人常用的外部服务，比如你自己的数据库连接。

3
Project（项目）

通过项目根目录的 .mcp.json 文件配置，可以提交 Git，整个团队共享。适合团队都需要的外部服务，比如共用的 Linear 或 Notion 连接。

3.4　MCP 的 Context 成本

MCP 有一个容易被忽视的成本：工具定义全量加载。每个 MCP 服务器连接后，它提供的所有工具定义都会加载进 context window，即使你这次根本不打算用它。

注意：MCP 工具定义不像 Skills 那样按需加载——它们是启动时全量加载的。连接的 MCP 服务器越多，占用的 context 越多，即使你没有使用它们。

管理建议：

  • 用 /mcp 命令查看当前已连接的服务器和工具列表
  • 禁用不常用的 MCP 服务器，减少不必要的 context 占用
  • 如果工具定义超过 context 的 10%，Claude Code 会自动切换到 tool search 模式——不再全量展示工具，改为按需搜索
MCP 和 Skills 都是"给 Claude 装工具"，区别是什么？
两者解决的问题完全不同。MCP 是外部服务连接——让 Claude 能访问本地代码之外的数据和服务，比如读取 Linear 的 ticket、查询数据库；Skills 是内部知识注入——告诉 Claude 执行某类任务的具体方法，比如"怎么做代码审查"、"怎么写文档"。MCP 扩展的是 Claude 能触达的数据范围，Skills 扩展的是 Claude 知道怎么做的事情范围。
模块四

Subagent — Claude 的分身

前三个工具都是在扩展"单个 Claude 实例"的能力边界。Subagent 走了另一条路：直接再开一个完整的 Claude 实例，让它独立去做一件事，做完把结论汇报回来。

4.1　Subagent 的本质：完整独立的 Claude 实例

Subagent 不是"主 Agent 的一部分"，而是一个完整的独立 Claude 实例，有自己的 context window、自己的 messages 数组、自己的 agent loop。

维度主 AgentSubagent
messages 数组 历史对话 + 工具调用 + 文件内容，几万 tokens 只有一条：主 Agent 传来的 prompt，几百 tokens
context window 随对话积累，越来越重 全新的，200k tokens 全部可用
能力 读写文件、运行工具、调用 Subagent 读写文件、运行工具（但不能再创建 Subagent）
生命周期 整个会话期间持续存在 完成任务后 context 被丢弃，只返回 summary

工作流程：

主 Agent Subagent ┌──────────────────────┐ ┌──────────────────────┐ │ messages = [ │ │ messages = [ │ │ 历史对话, │ │ task prompt │ │ 工具调用结果, │ ──→ │ ] │ │ 读取的文件, │ │ │ │ 几万 tokens │ │ 几百 tokens（干净） │ │ ] │ └──────────────────────┘ └──────────────────────┘ │ ↑ │ 独立执行： │ │ 读文件、运行工具 │ │ 探索代码库 │ ↓ │ 生成 summary │ │ │ 只返回 summary │ └────────────────────────────────┘ 主 Agent 的 context 保持干净，只增加了一条 summary
核心价值——Context Boundary（上下文边界）：探索性任务产生的大量中间过程（读了几十个文件、跑了几十条命令）不会污染主 Agent 的 context。主 Agent 只接收最终 summary，信噪比保持高位。
两个限制：Subagent 不能创建自己的 Subagent（防止无限递归）；完成后 context 被丢弃，不保留历史。

4.2　三大应用场景

A
独立视角——需要 fresh eyes 的任务

主 Agent 写完代码后，调用 Subagent 审查。Subagent 没有"我想做什么"的先入之见，只看"代码实际做了什么"，能发现主 Agent 因认知依赖而忽略的问题。Code Review 是这个场景的典型代表（下一节详讲）。

B
并行任务——多模块同时开发

主 Agent 作为 Project Leader，把独立的子任务分发给多个 Subagent 并行执行，最后整合结果。各 Subagent 的 context 互不干扰，不会因为一个模块的探索过程污染另一个模块的工作。

C
临时研究——保持主线干净

主 Agent 在开发过程中遇到"这个库怎么用"的问题，派 Subagent 去调研，返回 summary 后主 Agent 继续开发。调研过程中读的文档、跑的测试代码，全部留在 Subagent 的 context 里被丢弃，主线 context 完全不受影响。

Subagent 和直接开一个新对话有什么区别？
最关键的区别是项目 context 的自动传递。手动开新对话，你需要重新解释项目背景、粘贴相关代码、说明任务要求——这些工作全靠你手动完成。Subagent 由主 Agent 调用，主 Agent 会把必要的任务描述和项目信息打包进 prompt 传给它，Subagent 启动时就已经知道背景，不需要你手动解释。对于需要反复做的任务（比如每次写完代码都做 Code Review），Subagent 的效率优势非常明显。

4.3　重点展开：Code Review 场景

Code Review 是 Subagent 最经典的应用场景，值得深入理解。

为什么主 Agent 审查自己的代码不可靠？

主 Agent 在写代码时，已经形成了一套"我想做什么"的思维路径：

主 Agent 的思考过程： "我要实现功能 X" ↓ "先写 A 函数，然后 B 函数" ↓ "这样写应该可以" ↓ 写完代码，自我审查 // 问题：它"知道"自己想做什么 // 所以它会用"意图"去解读代码，而不是用"实际行为" // 边界情况、错误处理的漏洞，很容易被忽略

Subagent 没有这个包袱：

Subagent 的视角： "我看到这段代码" ↓ "目标是什么？实现了什么？" ↓ "有没有边界情况？错误处理？" ↓ 客观评价，只看代码实际做了什么
权责分离原则：Agent 的世界里也需要"做事的人 ≠ 审查的人"。就像公司里开发 ≠ QA，运动员 ≠ 裁判——既当运动员又当裁判，客观性无从保证。

在 Claude Code 里体现为：
Code writer（主 Agent）——有 edit 权限，负责写代码
Code reviewer（Subagent）——只有 read-only 工具，负责审查，不能直接修改

团队共用同一套 Reviewer 标准

一个常见的误解：团队用 Subagent 做 Code Review，是不是有"一个专门的 Reviewer Agent"在帮所有人审查？

不是。正确理解是：不是一个审查员，而是一套审查标准。

项目里有一个文件：code-reviewer.md ↓ 这个文件定义审查规则（审查什么、用什么标准、怎么报告） ↓ 张三的 Claude 用这个文件创建 Subagent → 按规则审查张三的代码 李四的 Claude 用这个文件创建 Subagent → 按规则审查李四的代码 ↓ 结果：大家的 reviewer 标准完全一致
类比：不是"公司有一个审查员"，而是"公司有一套审查规章制度，每个人用这套制度自查"。配置文件即标准，标准即一致性。

4.4　Persistent Memory：让 Subagent 跨 session 记住事情

Subagent 完成任务后 context 会被丢弃——但有时候你希望它"记住"上一次做了什么，比如 Code Reviewer 记得上次发现了哪些问题、上次已经审查到哪里。Persistent Memory 就是为此设计的。

它的工作方式：Subagent 完成任务后，把关键信息写入一个持久化的记忆文件；下次同一个 Subagent 被调用时，先读取这份记忆，带着"上次的经验"开始工作。

维度CLAUDE.mdPersistent Memory
性质 静态规则，手动维护 动态记忆，自动从对话生成
更新方式 你手动编辑文件 Subagent 每次运行后自动更新
典型内容 "用 Next.js 15，pnpm" "上次审查发现这个模块有性能问题"
跨 session ✅（文件持久存在） ✅（记忆文件持久存在）
Persistent Memory 的完整机制（记忆文件结构、更新策略、与 Memory 系统的关系）在学习笔记 II · 模块四有详细展开。

4.5　Preload Skills：为什么 Subagent 要预加载

主 Agent 的 Skills 是按需加载的——启动时只加载目录，用到时才加载完整内容。但 Subagent 通常会预加载它需要的 Skills 完整内容，而不是等到用时再加载。

主 AgentSubagent
Skills 加载方式 启动时加载目录，按需加载完整内容 启动时直接预加载指定 Skills 的完整内容
原因 生命周期长，有时间按需加载 生命周期短，任务开始就要立刻知道怎么做

Subagent 的生命周期很短——它被创建出来就是为了完成一个具体任务，完成后就消亡。如果还要在执行过程中再去按需加载 Skills，会浪费宝贵的时间。预加载让它一启动就具备完整能力，立刻投入工作。

模块五

Hooks — 100% 确定性的自动化执行

前四个工具都依赖 Claude 的"理解"——它读了规则，然后决定怎么做。但有一类需求不需要理解，只需要必定发生：每次编辑文件后格式化、每次完成任务后发通知、每次运行危险命令前拦截。Hooks 就是为这类需求设计的。

5.1　Hooks 解决什么问题

在 CLAUDE.md 里写"每次编辑文件后运行 Prettier 格式化"，Claude 大部分时候会照做——但不是每次。它可能在专注于某个复杂任务时忘掉这条规则，或者判断"这次改动很小，不需要格式化"。

CLAUDE.md 提示方式

Claude 读到规则 → 大部分时候会做 → 但有时会忘 → 不确定性存在

Hooks 方式

事件触发 → shell 命令必定执行 → 100% 确定性 → 无例外

Hooks 的本质：生命周期钩子。某个事件发生时，必定执行某个 shell 命令——不经过 Claude 的判断，不受 Claude 的注意力影响，机械地、确定地执行。

Hooks 配置在 settings.json 里，不是 CLAUDE.md。这个区别很重要：CLAUDE.md 是给 Claude 看的规则，Hooks 是给系统执行的命令，两者的执行者不同。

5.2　五个触发时机

Hooks 挂载在 Claude Code 的生命周期事件上，共有五个触发点：

事件触发时机能否阻止工具执行典型用途
PreToolUse 工具执行前 ✅ 可以（exit code 1） 安全检查、权限验证、阻止危险命令
PostToolUse 工具执行后 ❌ 不能（已执行） 自动格式化、日志记录、触发后续操作
UserPromptSubmit 用户提交 prompt 时 ✅ 可以 输入预处理、注入额外上下文
Stop Claude 完成任务时 — 发送完成通知、触发下游流程
Notify Claude 发出通知时 — 自定义通知渠道（Slack、邮件等）

最常用的两个是 PreToolUse 和 PostToolUse，分别对应"拦截"和"追加"两种模式：

用户发出任务 ↓ UserPromptSubmit Hook（可在此注入额外信息） ↓ Claude 决定调用工具 ↓ PreToolUse Hook（可在此检查并阻止） ↓ 工具执行 ↓ PostToolUse Hook（可在此追加操作，如格式化） ↓ Claude 完成任务 ↓ Stop Hook（可在此发通知）

常见用例组合：

  • PostToolUse + Edit/Write 匹配 → 每次编辑文件后自动运行 prettier --write
  • PreToolUse + Bash 匹配 → 检测危险命令（如 rm -rf），exit code 1 阻止执行
  • Stop → 任务完成后发送桌面通知或 Slack 消息
  • PostToolUse + 任意工具 → 记录所有操作日志

5.3　退出码协议：Hook 怎么和 Claude Code 通信

Hook 是一个 shell 命令，它通过退出码（exit code）告诉 Claude Code 接下来怎么做：

Exit Code含义PreToolUse 效果PostToolUse 效果
0 成功，继续 工具正常执行 正常继续
1 阻止 工具不执行，stderr 内容作为错误返回给 Claude 记录警告日志
2 注入消息 stderr 内容注入对话，工具仍然执行 stderr 内容追加到工具结果
类比理解：Claude Code 是厨师，Hook 是厨房里的小助手。
退出码 0 = 小助手点头（继续）
退出码 1 = 小助手举手（停！这个不能做）
退出码 2 = 小助手递纸条（有话说，但你继续做）

5.4　决策框架：Hook vs CLAUDE.md，用哪个？

判断一个需求该用 Hook 还是 CLAUDE.md，核心问题只有两个：

1
需要 Claude 的智能判断吗？

需要理解内容、看情况而定、创造性工作 → CLAUDE.md
纯机械动作、不需要理解内容 → 继续看第二个问题

2
每次都必须做，没有例外吗？

必须 100% 执行，不允许遗漏 → Hook
有时候做、有时候不做 → CLAUDE.md

判断维度用 Hook用 CLAUDE.md
能否一句话说清 "每次 X 就 Y"，机械重复 "看情况……"，需要判断
是否需要理解内容 不需要，只看动作类型和文件路径 需要，要理解文件内容或上下文
执行频率 每次触发都必须执行 有时执行，有时不执行
典型例子 格式化、日志、通知、安全检查 生成笔记、写文案、代码风格建议
Hook 能理解文件内容吗？比如"只格式化重要文件"？
不能。Hook 是"机器人"，它只能看到动作类型（Edit、Write、Bash…）和文件路径（通过环境变量传入），不能理解文件内容。"只格式化重要文件"这种需要判断的逻辑，要么写进 CLAUDE.md 让 Claude 决定，要么在 Hook 的 shell 脚本里用文件路径匹配规则来实现（比如只处理 src/ 目录下的文件）。

五工具对照表 — 本篇小结

五个工具各有定位，按"能力扩展层次"递进——从给 Claude 写说明书，到装知识插件，到连接外部世界，到任务分身，到自动化执行。理解它们的边界，才能在正确的场景用正确的工具。

6.1　五工具一览

工具 本质 加载时机 适合放什么 类比
CLAUDE.md 启动时自动读取的 prompt 启动时，永远在 context 技术栈、规范、命令、项目背景 员工手册

6.3　选择工具的决策路径

1
这件事需要 Claude 每次启动都知道吗？

是 → CLAUDE.md（技术栈、规范、命令）

2
这是一套可复用的执行方法，但不需要永远占 context？

是 → Skills（按需加载，节省 85% context）

3
需要的数据不在本地，在外部服务或数据库？

是 → MCP（连接 Linear、数据库、Notion 等）

4
需要独立视角、并行执行、或隔离探索过程？

是 → Subagent（独立 context，保持主线干净）

5
某个动作必须 100% 发生，不能依赖 Claude 记得？

是 → Hooks（事件触发，机械执行，无例外）

它们可以组合使用：CLAUDE.md 告诉 Claude 项目规范 → Skills 告诉 Claude 怎么做 Code Review → Subagent 用 fresh eyes 执行审查 → Hooks 确保每次提交前必定触发审查 → MCP 连接 Linear 读取相关 ticket 背景。五个工具各司其职，组合起来才是完整的定制化工作流。
